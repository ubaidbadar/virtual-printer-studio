# Restora order-print test status

The live authenticated order-print flow at https://app.restora.live/ has now been checked at the browser layer; the browser-to-Windows-printer path remains unverified. See the authenticated checks below. Earlier Windows acceptance runs used GDI test documents and the desktop application's own buttons, not Restora or a browser print dialog.

Public-source inspection on 2026-11-17 found the deployed entry bundle `index-RMwExQDm.js`. Its order-print function tries a server `/print-jobs` request, then a branch-configured local print bridge, then a browser iframe fallback. The fallback calls the iframe's `window.print()` and sets an 80 mm custom page size. Receipt and kitchen-slip layouts differ. This is source inspection, not evidence that a live print succeeded.

A real test needs a signed-in Restora browser on the same Windows machine as the installed virtual queue and an existing authorized test order. Record which path is used; a server/bridge success message alone does not prove the local virtual queue received a job. Verify the resulting PDF against the order's items, quantities, prices, tax, totals, payment stamp, notes and any logo. Check receipt width, long-order pagination, clipping, reprinting and duplicate handling. Use the actual order Print action; browser Save as PDF bypasses the Windows printer and is insufficient.

The initial public-source inspection had no authenticated session. The subsequent authenticated browser checks are described below.

## Reuse and structure review

The Rust workspace separates transport/delivery and shared domain data into `crates/core`, with Windows-specific operations under `src/platform`. The UI shares `PrinterCard` and a central `Tokens` global. Those are concrete reusable boundaries.

The source is not fully refactored. `src/service.rs` combines worker orchestration, native operations and persistence, while `src/main.rs` combines CLI startup, UI binding and settings synchronization. Some PowerShell automation locator/wait logic is duplicated. Refactoring should preserve the verified behavior and be followed by relevant native regression tests.

The application's design is **not 100% matched** to the supplied references. See [client testing](client-testing.md) for the measured differences. No new design-conformance or Restora-compatibility claim is made here.

## Authenticated browser checks (2026-11-17)

Using the owner's explicitly supplied test account, the browser test operated an existing order's **Print receipt**, **Print kitchen slip**, and receipt reprint actions. No order items, payment status, or restaurant settings were changed. All three server print requests returned HTTP 409; the site then invoked its browser iframe print fallback. These observations supersede the earlier statement that the authenticated flow had not been exercised.

Private Chromium reference renders contained the order items and receipt total. All three corrected renders fit on one approximately 80 mm wide page. An early reference test omitted the iframe document's doctype and incorrectly reported a footer-only second page. Preserving the doctype reproduces the site's standards-mode layout; that earlier pagination finding was a test-harness error, not an established Restora defect. Account data, credentials, HTML and PDFs remain outside the repository and were not published as CI artifacts.

The remaining check is the actual browser-to-Windows-queue path. A proposed temporary Windows 11 test would install the existing tested application, create a uniquely named PDF queue, authenticate in headful Edge, operate those same three existing-order print actions, and verify the resulting Microsoft-driver PDFs. It would create no orders, change no payments, upload no order contents/screenshots/PDFs, log only redacted status and page dimensions, and remove temporary credentials and queues afterward.

The owner subsequently authorized this temporary, no-export Windows test. The connected GitHub integration returns HTTP 403 (`Resource not accessible by integration`) for repository Actions secrets. It can push source and dispatch workflows, but cannot supply the temporary protected credentials needed by this job. Credentials must not be substituted into workflow inputs, source or logs. The Windows Restora execution remains unverified. The earlier application-only Windows checks remain valid independently of this site-specific check.

## Reproducible private acceptance

The manual **Private Restora Windows print acceptance** workflow uses the existing x64 package on an actual Windows 11 ARM64 runner (x64 emulation). The default `live-restora` scenario requires protected `RESTORA_TEST_EMAIL` and `RESTORA_TEST_PASSWORD` repository secrets. This scenario does not upload artifacts or private diagnostics. Delete temporary secrets after the test. Run [44072663786](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44072663786) stopped at the missing-secret guard before signing in or loading order data.

`scripts/qa/restora-print.ps1` creates a unique native PDF queue, temporarily selects it as the default, and runs headful Edge with kiosk printing. It restores the previous default, removes the test queue, and deletes the browser profile, capture state, logs and PDFs in a `finally` block. Use this wrapper on a disposable elevated Windows session. A runner crash can prevent cleanup; hosted VMs are destroyed after the job.

`scripts/qa/restora-print.py` signs in, reads the existing order response, operates receipt/kitchen/reprint, observes the site's real iframe `window.print()` calls without replacing them, and waits for three distinct deliveries through the app. It checks all printed lines, order item names and total, Microsoft PDF producer, 80 mm width, and footer-only pagination. The redacted report contains only counts, booleans, page dimensions, HTTP statuses and static failure messages. Layout failures fail acceptance even if delivery and content pass. Logos, visual alignment, every tax/payment variation and long-order behavior still require additional fixtures; this test does not claim exhaustive coverage.

The same script's explicitly separate `--reference-only` mode was executed in local Chromium with protected environment credentials. It preserves the iframe doctype, checks its original rendering mode and reproduces all three print actions. This mode uses Chromium's PDF renderer and cannot establish Windows printer compatibility.

The independent `synthetic-browser` workflow scenario runs `browser-print.py` through the same Windows fixture and headful Edge configuration without credentials. Its static receipt tests three real iframe print submissions, queue delivery, text, producer, page sizes and duplicates. It does not access Restora and must not be reported as an authenticated order-print pass.

Synthetic run [44073123455](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44073123455) delivered three distinct Microsoft-driver PDFs on Windows 11 build 26200. Acceptance failed: all pages were Letter (215.9 × 279.4 mm), rather than the HTML's requested 80 × 150 mm, and text extraction returned empty strings. Static PDFs collected in [44073787170](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44073787170) showed that Edge had converted text into vector outlines. Visual inspection and independent local OCR confirmed the fixture words were present. Windows-local OCR now verifies outlined text without sending it to a service. The synthetic-only scenario can export its static test PDFs for diagnosis; live-account exports remain disabled by both script and workflow guards.

Run [44074786533](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44074786533) verified all three synthetic receipt/kitchen/reprint outputs with Windows' local OCR: content and delivery passed; 80 mm layout failed. The standard Windows print-ticket API also validated the 80 × 150 mm request as Letter, and the driver's advertised paper list had no 80 mm entry. `NoConflict` alone is therefore insufficient: inspect the returned dimensions. This configuration cannot claim 80 mm receipt support. No system driver definitions were modified.

Redacted evidence: [corrected live browser reference](evidence/restora/browser-reference.json), [Windows synthetic results](evidence/restora/windows-browser.json), and [driver media validation](evidence/restora/driver-media.json). These files contain no order contents, credentials or session state. The source checks and native generic printer regression passed in [Desktop checks 44074732081](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44074732081).

The final configuration probe [44076652624](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44076652624) registered a uniquely named 80 × 150 mm Windows form and requested that form through the driver's native DEVMODE validation API. The driver returned paper ID 1 (Letter), 215.9 × 279.4 mm, so the test correctly refused to apply the unsupported settings. Three subsequent Edge jobs again preserved their content and used Letter. The temporary form, queue and private working files were removed. [Custom-form result](evidence/restora/custom-form.json).

Changing browser CSS or merely registering a form does not fix this tested configuration. 80 mm receipt support needs a rendering/driver path that accepts that media; the current Microsoft-driver path is not certified for it. The final code revision `ed9b668` passed Linux/Windows formatting, tests, Clippy, release builds, PowerShell parsing and the native generic printer regression in [Desktop checks 44076596647](https://github.com/ubaidbadar/virtual-printer-studio/actions/runs/44076596647).
